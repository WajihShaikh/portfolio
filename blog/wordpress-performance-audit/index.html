How I approach a WordPress performance audit

A performance audit is most useful when it identifies why a page is slow, not merely which score is low. This is the sequence I use to separate hosting, theme, plugin, media and third-party problems.

Written by Wajih Shaikh

Senior WordPress Developer & Web Designer

What should a WordPress speed audit tell you? Which templates are affected, where the largest costs come from, what to change first and how to check that the website still works. A score alone is not an action plan.

Start with the page users actually visit

I test representative templates rather than only the homepage: a service page, product page, archive and any page with forms or embeds. Different templates often have different bottlenecks.

Separate field data from lab data

PageSpeed Insights field data describes real Chrome users when enough data exists. Lighthouse is a controlled diagnostic. I use both, but I do not treat a single lab run as proof of the real user experience.

Core Web Vitals: the “good” targets, not results from my projects
MetricWhat it coversGood target
LCPLoading the largest visible content element2.5 seconds or less
INPResponsiveness to user interactions200 milliseconds or less
CLSUnexpected layout movement0.1 or less

Assess these at the 75th percentile of real visits, with mobile and desktop considered separately. Google’s Web Vitals guidance explains the thresholds. If a site lacks enough field data, report that limitation rather than presenting lab scores as field results.

Find the largest cost before changing plugins

I review the LCP element, request waterfall, image dimensions, font files, JavaScript execution and layout shifts. The highest-impact issue might be a hero image, a third-party widget or server response time—not the cache plugin.

Change one layer at a time

Image delivery, caching, CSS, JavaScript, fonts and hosting are separate layers. Small controlled changes make it possible to confirm what helped and avoid breaking checkout, forms or tracking.

Verify the result

I retest the same templates and interactions, check responsive layouts, clear relevant caches and watch for delayed layout shifts. Performance work is complete only when the site still behaves correctly.

  1. Keep a comparison recordRecord the URL, device setup, test conditions and changes made. Compare like with like.
  2. Try the important interactionsOpen the mobile menu, expand content, submit a test form and run a test checkout where applicable.
  3. Explain what remainsDocument third-party costs, hosting limits and any feature trade-offs. Don't promise a score that depends on conditions outside the build.

For examples of the types of business websites I work on, explore the portfolio. Those showcases are not before-and-after performance benchmarks.

The practical takeaway

Start with evidence, address the largest bottleneck, then check both the metrics and the business-critical interactions. A faster page that breaks the inquiry form is not an improvement.
